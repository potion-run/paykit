paykit keeps its event log, receipts, state and read models in SQL. The database is a port: the
model asks for an executor, and a deployment chooses the target. Nothing in the model imports a
driver, `check()` still answers from one local read, and a Worker never runs a migration.

## One port, two obligations

`Paykit.Database` is the port. A target supplies one `DatabaseService`:

```ts
interface DatabaseService {
  dialect: "sqlite" | "postgres";
  schema?: string; // the Postgres schema, when the target has one
  runtime: Effect<SqlExecutor, never, RuntimeContext | Scope.Scope>; // per execution
  migrate?: {
    // absent when the target cannot migrate
    identity: Input<Record<string, unknown>>; // non-secret identity of the target
    connect: Effect<Effect<SqlExecutor, MigrationApplyError, Scope.Scope>, never, RuntimeContext>;
  };
}
```

`runtime` is opened per execution and closed when the event settles, which is the only pooling
shape workerd allows. `migrate.connect` is a separate obligation because a migration needs one
dedicated session: the registry's bookkeeping queries are unqualified, so Postgres scopes
`search_path` around them, and a pooled connection would spread the statements across sessions.

The two connections are also separate because they exist in different places. A Hyperdrive
connection string is only valid inside the Worker, so the deploy cannot use it; migrations take the
origin URL, or the target has no `migrate` at all. `identity` is the non-secret identity of the
target — a URL digest on Postgres, a filename on SQLite — and never the URL itself, because it is
persisted in the migration Action's input. `schema` names the Postgres schema (`billing` by default;
`public` is never touched) and is ignored by SQLite.

## Choose a target

The layers ship one per target and are imported from their own export condition, never the barrel.
The driver is a peer dependency, so a Worker that imports the package must not pull `pg` or
`bun:sqlite` into its bundle, and a Bun test must not pull a D1 binding.

| Target | Layer | Runtime | Migrations |
| --- | --- | --- | --- |
| SQLite under Bun (dev, tests) | `@potion.run/paykit/Database/Sqlite` | `bun:sqlite` over one file | `migrate.connect` opens the same file |
| D1 in a Worker | `@potion.run/paykit/Database/D1` | the D1 binding, asynchronous | none — the D1 resource applies the directory |
| Postgres (Hyperdrive, Neon, Aurora, plain) | `@potion.run/paykit/Database/Postgres` | Hyperdrive inside a Worker, `pg` where sockets exist | `migrate.connect` uses the origin URL |

Provide one layer where the deployment builds its world, and read the executor from the service:

```ts
import { Paykit } from "@potion.run/paykit";
import { Postgres } from "@potion.run/paykit/Database/Postgres";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";

Effect.gen(function* () {
  const url = yield* Config.Redacted("POSTGRES_URL");
  const store = Postgres(url, { schema: "billing" });

  yield* Paykit.registerMigrations("Billing").pipe(Effect.provide(store));
  // a request later reads `store`'s executor from `Paykit.Database`
});
```

**SQLite** is the development and test target. One file, one process, migrations and requests share
the same connection, and there is nothing to provision. It is what the SQL tests run.

**D1** is the Worker target without a separate migration step. The database resource applies the
committed `./migrations` directory itself, so the port serves runtime reads and the layer carries no
`migrate`: `registerMigrations` is a no-op there, and asking for `migrate: true` fails with a message
naming this reason.

```ts
import * as Cloudflare from "@alchemy.run/cloudflare";

export const BillingDatabase = Cloudflare.D1.Database("BillingDatabase", {
  migrations: "./migrations",
});
```

D1 has no interactive transactions: one `batch` is the closest it offers. That is fine for the
session and small-read workload it usually carries, but a store or plugin that needs a real
transaction belongs on Postgres.

**Postgres** is the target for a durable deployment. In a Worker it is reached through Hyperdrive,
which pools the connections workerd would otherwise open per request; a test or a long-lived
service uses `pg` directly. When the runtime and the deploy use different credentials — the usual
Hyperdrive arrangement — `migrate.connect` names the origin connection and `runtime` keeps the
binding. Neon, Aurora and a plain connection string are the same two obligations with a different
driver.

## The description, the files, and the delta

`BILLING_SCHEMA` is the schema as typed data: tables, columns and indexes. `migrationFiles()` renders
it for a dialect, and the files committed under `examples/*/migrations/` are that rendering. DDL text
is never hand-written.

```ts
import { migrationFiles } from "@potion.run/paykit";

const files = migrationFiles({ dialect: "postgres", schema: "billing" });
```

A schema change moves through one pipeline:

1. **Describe.** Change `BILLING_SCHEMA`. A column type is stated once; the renderer owns
   `INTEGER` versus `BIGINT` for epoch millis, `AUTOINCREMENT` versus `BIGSERIAL`, schema
   qualification and identifier quoting.
2. **Render.** `pnpm schema <dialect>` rewrites the committed files for `sqlite` or `postgres`.
3. **Check.** `pnpm migrations:check` fails when a committed file is not the rendering of the
   current description.
4. **Apply.** The deploy runs the shipped files through `@alchemy.run/sql/Migrations`, which owns
   the bookkeeping table and the content hashes.
5. **Converge.** The deploy reads the live catalog and adds the columns and indexes the description
   states and the database lacks.

| Command | What it does |
| --- | --- |
| `pnpm migrations:check` | Fails when a committed file disagrees with `BILLING_SCHEMA` for its dialect |
| `pnpm schema <dialect>` | Re-renders the committed files for `sqlite` or `postgres` |

The files are the baseline a new database starts from. Convergence is the delta for one that already
has a history. A new table is rendered as a file; a new column or index on an existing table is a
delta the deploy adds without editing what it already applied. Each step is independently
idempotent, so a crash mid-deploy converges on the next run.

## What a deploy guarantees, and what it refuses

`Paykit.registerMigrations` registers one Action per migrated target, with this input:

```ts
{ identity, schemaFingerprint, migrationFingerprint, dialect }
```

A deploy therefore:

- applies every shipped file once, in order, and records its content hash;
- re-runs the Action when a file is added, the description changes, or the target database is
  replaced — and does no database work when none of those changed;
- runs only at apply: never at plan, never inside the deployed runtime;
- binds the Action's output into the host environment, so the Worker depends on it and cannot start
  against a half-migrated database;
- converges idempotently — a missing column or index is added, and a present one is left alone.

It refuses:

| Change | Answer |
| --- | --- |
| Drop, rename, retype or narrow a column or table | Never. That is a reviewed migration with its own record, not a deploy. |
| Add a `NOT NULL` column with no default | A typed refusal naming the table and column, because the table may already have rows. |
| Rewrite or remove a file a database already applied | The registry refuses it: the applied hash is history. |
| Put the billing tables in `public` | Refused. Postgres gets its own schema. |
| Migrate D1 through the port | No `migrate` on the target: the D1 resource applies the directory. `migrate: true` fails, naming the reason. |

## Auth and billing own their own tables

Better Auth and paykit are two products with two migrators. Neither reads or writes the other's
tables, so one database with two disjoint table families and two databases are both supported — and
a version bump in one never rewrites the other's history.

| Owner | Migrator | Tables |
| --- | --- | --- |
| Better Auth | `@alchemy.run/better-auth` | the auth tables, plugins included |
| paykit | `Paykit.registerMigrations` | `billing_event`, `billing_receipt`, `billing_state`, `billing_outbox`, `billing_schedule`, `billing_rm_*` |

The split matters most on D1. Sessions are a small, transactional read/write workload that D1 serves
well; the billing store is the event log, and a plugin that needs interactive transactions has no
way to get one there. Put those on Postgres, either in a second database or in the same one under a
different table family.

The decisions are [ADR 0049](https://github.com/potion-run/paykit/blob/main/docs/adr/0049-the-billing-schema-is-a-description-and-the-deploy-converges-it.md)
for the port and the convergence, and [ADR 0003](https://github.com/potion-run/paykit/blob/main/docs/adr/0003-the-deploy-provisions-the-vendor.md)
for why a deploy retains what a bill references.

See [Auth](/auth/) for the session side, including what a deployment must preserve across deploys.
